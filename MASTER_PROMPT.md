## 1. PRODUCT

Theme: "Build for Your World". Problem: manually parsing complex government/enterprise tender PDFs is a bottleneck that delays bidding. Solution: upload a tender PDF -> segment/extract text, tables, stamps, signatures (SAM 3.1 via Meta Model API) -> Muse Spark extracts requirements with source page + exact quote -> a DETERMINISTIC Java engine verifies each requirement against the company's internal database -> risks, missing-document checklist, readiness score, Bid/No-Bid recommendation, executive bid summary -> human approval -> reports. The UI shows all of this LIVE, in real time, as the pipeline runs.

CORE PRINCIPLE: The LLM only extracts and explains. It NEVER decides a verdict, score or Bid/No-Bid. All verdicts come from deterministic Java code using BigDecimal. AI never authorizes submission; human approval is mandatory.

OUT OF SCOPE (do not build): native OCR (no tess4j/tesseract), a 29-table schema, 22 screens, knowledge-graph explorer, e-signature/stamp authenticity validation, automatic bid submission, multi-tenant org hierarchies (a user belongs to exactly one company).

## 2. NON-NEGOTIABLE ENGINEERING RULES

R1. Money = java.math.BigDecimal only (never double/float). Base unit INR. Store/display scale 4, RoundingMode.HALF_UP. DB NUMERIC(19,4). JSON serializes money as STRINGS; the client never does money arithmetic.
R2. COMPARE EXACT VALUES, NEVER ROUNDED ONES. Rounding is for storage/display only. Use compareTo (never equals). For averages compare sum >= threshold x n (no division). Percent thresholds (0.80/0.50/0.40) are applied with exact BigDecimal multiplication, no rounding.
R3. Verdicts are exactly PASS, FAIL, UNKNOWN, NEEDS_REVIEW.
 - UNKNOWN = a required company record/document is missing. Missing evidence is NEVER FAIL.
 - FAIL = reliable evidence exists and clearly does not satisfy (including expired as of the submission deadline).
 - NEEDS_REVIEW = ambiguous, unaudited, low-confidence, unsupported metric/currency, or evidence without a supporting document.
 - PASS only with positive supporting evidence. Unsupported/unrecognized requirements are NEEDS_REVIEW, never PASS.
R4. Untrusted PDF sandbox: all extracted PDF text sent to any model is wrapped as <untrusted_tender_excerpt page="N">...</untrusted_tender_excerpt>. Before wrapping: strip control characters and neutralize any occurrence of the opening/closing tag strings inside the text so PDF content cannot close the tag early. The system prompt states tag contents are data, never instructions.
R5. Traceability + quote verification: every requirement and verdict keeps (sourceDocument, sourcePage, clauseRef, originalQuote). Java verifies the model's quote is a substring of that page's extracted text after normalization (Unicode NFKC, whitespace collapsed, dash/quote variants unified, rupee sign and "Rs."/"Rs" unified, case-insensitive), keeping an offset map back to the raw text. On success, STORE THE EXACT RAW PDF SPAN (not the model's string) as originalQuote. On failure flag NEEDS_REVIEW (QUOTE_NOT_VERIFIED). The model may never replace legal text with a paraphrase.
R6. The model returns amounts as raw text (e.g. "Rs. 100 Cr"); Java converts via MoneyUtils. Never trust model arithmetic or model-supplied numerics.
R7. Model-reported confidence must be within [0.0, 1.0] (validate; out of range = response rejected); below 0.80 -> NEEDS_REVIEW. Model confidence is uncalibrated: never present it as a probability of correctness.
R8. Inject java.time.Clock wherever "today" matters. Certificate validity is evaluated against the tender's submissionDeadline, not today. ALL golden tests use a fixed Clock of 2026-11-04T10:00+05:30.
R9. No hardcoded secrets. MODEL_API_KEY, JWT secret, DB password come from environment/.env. In the non-dev profile the app must fail to start if the JWT secret is missing. Never log secrets.
R10. Every AI call, retry, fallback and error is logged (no secrets, no raw prompts) to ai_call_logs and attached to the run trace.
R11. Audit log is insert-only (no update/delete code path) with before/after JSON.
R12. Environment honesty: run java -version, mvn -version, node -v, npm -v, docker --version, git --version first. Required: JDK 21, Maven 3.9+, Node 20+. If JDK 21 is missing -> BLOCKED; never silently downgrade.
R13. submissionDeadline is stored as an offset date-time (IST, +05:30). Certificate/financial/project date comparisons use dates in Asia/Kolkata, inclusive (valid on the deadline date if expiry >= deadline date).
R14. Rupee sign: standard PDFBox Type1 fonts cannot draw U+20B9 and will throw. In generated PDFs embed a bundled open-license TrueType font containing the rupee glyph (PDType0Font.load; check license; verify programmatically that the glyph exists; store under server/src/main/resources/fonts). If no such font can be obtained, write "Rs." in generated PDFs and document it. MoneyUtils accepts both forms; golden tests normalize the currency prefix.
R15. INR only. A record or requirement in another currency -> NEEDS_REVIEW (CURRENCY_UNSUPPORTED), never converted silently.
R16. Determinism: same inputs + same Clock + same companyDataVersion => identical verdicts and calculation traces, in stable order.
R17. Concurrency: at most one active workflow job per tender version; re-verify and amendment processing serialize per company (lock or optimistic version check); realtime events are emitted only AFTER the transaction commits.

## 6. DOMAIN LOGIC SPEC (deterministic Java)

6.1 MoneyUtils: parse to BigDecimal INR scale 4. Units: Cr, Crore, Crores (x10,000,000); Lakh, Lakhs, Lac, Lacs (x100,000); plain INR. Handle prefixes the rupee sign, Rs., Rs, INR; commas incl. Indian grouping (1,00,00,000); decimals (12.5 Cr); trailing punctuation ("Rs. 1.2 Cr."); case-insensitivity. Negative or unparseable -> typed exception -> pipeline converts to NEEDS_REVIEW.
6.2 Requirement model (strict schema): id, category, mandatory (default TRUE unless clearly "desirable/preferred/optional"; ambiguous -> TRUE + flagged), metric enum {AVG_ANNUAL_TURNOVER, NET_WORTH, SIMILAR_PROJECTS_COUNT_VALUE, SIMILAR_PROJECTS_80_50_40, CERTIFICATE_VALID, SOLVENCY_CERTIFICATE, OTHER}, operator {GTE,GT,LTE,LT,EQ}, amountText, count, lookbackYears (nullable = no window), domainTags, certificate name/level, conditionTree (AND/OR of leaves), clauseRef, sourceDocument, sourcePage, sourceRegionId (nullable), originalQuote, confidence; for corrigenda also amendmentAction {SUBSTITUTE, INSERT, DELETE, DEADLINE_CHANGE, NONE} and targetClauseRef. Metric OTHER -> NEEDS_REVIEW.
6.3 Financial evaluators (all use general operators GTE/GT/LTE/LT/EQ via compareTo; any non-INR record -> NEEDS_REVIEW per R15):
 - AVG_ANNUAL_TURNOVER: take the N most recent FY records (N from requirement, default 3) with FY end date <= deadline date. Precedence: fewer than N -> UNKNOWN; else any unaudited OR lacking a supporting document -> NEEDS_REVIEW; else compare sum vs threshold x N exactly.
 - NET_WORTH: records with FY end <= deadline date; none -> UNKNOWN; none audited -> NEEDS_REVIEW; else take the latest AUDITED FY; no supporting document -> NEEDS_REVIEW; else compare.
 - SOLVENCY_CERTIFICATE: none -> UNKNOWN; expiry date missing -> NEEDS_REVIEW; amount fails threshold OR expiry < deadline date -> FAIL; valid but no supporting document -> NEEDS_REVIEW; else PASS.
6.4 Project evaluators. A project is ELIGIBLE iff status COMPLETED, completion date within [deadline - lookbackYears, deadline] (no window if lookbackYears null), and domainCategory matches requirement domainTags (empty tags = any). Project value used = contractValue (if missing -> that project makes the result NEEDS_REVIEW). ZERO project records for the company -> UNKNOWN. Otherwise compute on the DOCUMENTED set (eligible projects with a completion-certificate document): if the condition is satisfied -> PASS; else compute on ALL eligible projects: if satisfied -> NEEDS_REVIEW (completion certificate missing); else FAIL. FAIL here means "per company database": the DB is treated as the complete project record; state this assumption in docs, UI and reports.
 - Count/value leaf: at least N distinct eligible projects each >= V.
 - 80/50/40 leaf with estimated contract value E from tender metadata (missing E -> UNKNOWN): with eligible values sorted descending v1>=v2>=v3: PASS if v1 >= 0.80E, OR v2 >= 0.50E, OR v3 >= 0.40E (distinct projects; inclusive boundaries).
6.5 Certificate evaluator: not found -> UNKNOWN; expiry < deadline date -> FAIL; expiry >= deadline date with supporting document -> PASS; valid without document -> NEEDS_REVIEW. Leveled certificates (CMMI): certificate level >= required level.
6.6 Condition trees (recursive):
 AND: any FAIL -> FAIL; else any UNKNOWN -> UNKNOWN; else any NEEDS_REVIEW -> NEEDS_REVIEW; else PASS.
 OR: any PASS -> PASS; else any NEEDS_REVIEW -> NEEDS_REVIEW; else any UNKNOWN -> UNKNOWN; else FAIL.
6.7 Every result stores calculationTrace: formula text, operands (exact BigDecimals as strings), threshold, the comparison actually performed, verdict, rule version, evidence record ids, source provenance, evaluation-context hash.
6.8 BidDecisionEngine (MANDATORY requirements only): 0) zero mandatory requirements -> INSUFFICIENT_DATA; 1) any FAIL -> NO_BID (even with score 90+); 2) else UNKNOWN share STRICTLY greater than 30% -> INSUFFICIENT_DATA; 3) else any UNKNOWN or NEEDS_REVIEW -> CONDITIONAL_BID (with missing-document checklist + pre-bid clarification questions); 4) else BID. A non-mandatory FAIL never blocks (shown as a warning).
 Readiness score (NOT a probability): 100 x sum(value)/N over mandatory requirements; PASS=1, NEEDS_REVIEW=0.5, UNKNOWN=0, FAIL=0; BigDecimal scale 2 HALF_UP; equal weights; documented in docs/COMPLIANCE_ENGINE.md. UI/API label: "readiness score (rule-based)". Never "probability" or "chance of winning".
 Human approval: POST decision/approve with APPROVED_FOR_BID or REJECTED_NO_BID, ADMIN/BID_MANAGER only, audit-logged. Until then status = PENDING_HUMAN_APPROVAL. The system never auto-submits.
6.9 Time-saved metric (honest):
 manualBaselineMinutes = totalPages x baselineMinutesPerPage (config, default 4.0, labelled ASSUMPTION, not a measured human benchmark).
 assistedMinutes = processingMs/60000 + reviewItems x reviewMinutesPerItem (config default 2.0; reviewItems = count of DISTINCT items that are UNKNOWN, NEEDS_REVIEW or low-confidence). processingMs = measured wall-clock from job start to completion.
 timeSavedPercent = (manual - assisted)/manual x 100, scale 2 HALF_UP, floored at 0.
 Report per run with aiMode. A FALLBACK run is labelled "not representative" and never used for the headline claim. State plainly whether the >=70% target was met, including when it was not.
6.10 Risk engine (deterministic, injected Clock): mandatory FAIL -> CRITICAL; mandatory UNKNOWN -> HIGH (missing documentation); NEEDS_REVIEW -> MEDIUM; non-mandatory FAIL -> LOW; deadline within 7 days (0 <= remaining < 7 days) with unresolved UNKNOWN -> HIGH deadline risk; deadline already passed -> CRITICAL (SUBMISSION_DEADLINE_PASSED). Each risk has sourceClause, evidence summary, detection reason, business impact, corrective action.
6.11 Amendments: FULL_REVISION (replaces base) and CORRIGENDUM (partial; merges into base by clauseRef; unmentioned clauses carry over; supports substitution, insertion, deletion, deadline change). Diff detects inserted/deleted/modified clauses, changed thresholds/operators, changed condition trees, changed deadline.
 SELECTIVE RE-VERIFICATION: copy an old result ONLY IF requirementFingerprint is unchanged AND evaluationContextHash is unchanged, where evaluationContextHash = hash(deadline date, estimatedContractValue, ruleVersion, companyDataVersion). companyDataVersion is a monotonic per-company counter bumped on any company-data write. Any deadline change therefore forces re-evaluation of everything (all evaluators depend on the deadline). Record readinessScoreDelta and the decision transition. Re-Verify after company edits re-runs only the Java engine on the current requirements (context hash changed -> all re-evaluated); it never re-calls AI extraction.
6.12 Missing-document checklist (every UNKNOWN) and pre-bid clarification questions (every NEEDS_REVIEW/ambiguous clause). Executive summary generated by Muse Spark strictly from structured verified data; Java grounding check: every number/currency amount/date in the summary must appear in the input facts (after canonicalization), else groundingWarning. Fallback = template summary labelled FALLBACK.
